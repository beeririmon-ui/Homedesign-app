## 2. הבריף
כל הפעלה מקבלת בריף כתוב בריפו (`BRIEF-*.md`), עם:
1. המשימה וגבולותיה, וציטוט ההנחיה של המשתמש עם תאריך.
2. **ההגדרות המדויקות של מה שמחושב.** דוגמה ללקח: "התרחיש הגרוע בכל שיטת משלוח" גרם ל-162 העלאות מחיר שגויות. צריך היה: "שיטת המשלוח שבה אנחנו שולחים בפועל".
3. קבצי הקלט, בנתיב.
4. התוצרים: נתיבים ופורמט. **רק קבצים חדשים.** קובץ משותף (`products.json`, `seen.json`, כרטיסים קיימים, `targets.json`) משנה רק המנהל, אחרי שקרא את התוצר.
5. תנאי קבלה, כולל "כל מספר עם מקור או סימון הערכה".
6. הכללים הקבועים: מפתחות, בלי פנייה, בלי commit, `-I` לקריאת מטמון.

## 3. שני מצבים: דיווח, ואז החלה
- **מצב דיווח (ברירת מחדל):** הסוכן מחשב וכותב תוצר. לא נוגע בנתונים חיים.
- **מצב החלה:** רק אחרי שהמנהל קרא את הדיווח, ורק לפי בריף שני קצר עם ההגדרות שאושרו.
- מה שמשנה מחירים, כרטיסים, עמדות או מסמכים מחייבים עובר תמיד דרך שני המצבים.

## 4. כמה במקביל, ובאיזה סדר
- לכל היותר **2 סוכנים כבדים** במקביל (מחקר רשת, ריצות API). בשבוע הזה 10 ריצות כבדות ב-3 ימים הגיעו למגבלה השבועית, ושני סוכנים נעצרו באמצע.
- עבודה בלתי תלויה רצה במקביל; עבודה שכותבת לאותם קבצים לא.
- לפני ריצה כבדה: האם החלטה פתוחה של המשתמש הופכת אותה למיותרת? (סבב 6: שלוש הריצות נתנו כרטיס אחד; ההחלטות R6Q1–4 שוות 38 עמדות-סגנון.)

## 5. אחרי כל ריצה
1. המנהל מאמת: JSON תקין, סריקת סודות, בלי פרטים אישיים.
2. הלוח: שורה ביומן, והחלטות חדשות ב-`status/decisions.json` **וב-db של הסטודיו** באותו יום.
3. Commit של מצב שלם בלבד. מצב ביניים של סוכן לא נכנס לענף; אם ה-stop hook דורש commit, מסמנים WIP ומחזירים לפני הפרסום.
4. הסטודיו מתפרסם מחדש רק ממצב שלם, אחרי build רגיל (לא offline) ו-7 בדיקות העשן.

## 6. החלטות
- כל שאלה למשתמש נכנסת ל-`decisions.json` עם המלצה, מה היא חוסמת, ומקור.
- **ישיבת החלטות** אחת לשבוע: עד 10 פריטים, מסודרים לפי מה שהם חוסמים. החלטה שלא נענתה שבועיים נסגרת או מסומנת כמוחלפת, עם הסבר.
- החלטה שהמשתמש ענה עליה בשיחה נרשמת מיד, ב-`studio-rules.md` (ז) וב-`decisions.json`, וה-db מתעדכן.
