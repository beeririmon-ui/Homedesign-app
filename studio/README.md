# הסטודיו: ממשק ניהול פנימי

כלי פנימי (back-office) לכל תהליך העבודה של המותג. הוא מציג את ההחלטות הפתוחות, החדרים והפריימים, המוצרים, הרווחיות, תקציב ההקמה, דוחות ה-QA והיומן. במסך המוצרים אפשר גם לערוך מוצרים ולהוסיף לידים. זה **לא** האתר ללקוחות, ואין לו קשר ל-`site/`.

הדף מתפרסם כ-claude.ai Artifact (המנהל מפרסם) עם capabilities ‏`{db:{}, user:{}}`, כדי שאפשר יהיה לפתוח אותו מהטלפון ומאפליקציית Claude.

**הריפו נשאר מקור האמת.** ה-db של ה-Artifact שומר רק תשובות להחלטות, תיקונים למוצרים, לידים חדשים והגדרות. הם חוזרים לריפו דרך `studio/apply_edits.py`.

## בנייה מחדש

```bash
python3 studio/build.py                        # בנייה רגילה
python3 studio/build.py --offline              # בלי רשת: מוצר בלי תמונה במטמון מקבל מקום שמור
python3 studio/build.py --economics-dir DIR    # בדיקה עם קבצי כלכלה מתיקייה אחרת
```

- דרוש Python 3 ו-Pillow, בלי תלויות נוספות. הסקריפט רק **קורא** מהריפו ובונה את `studio/dist/` מאפס.
- **מטמון:**
  - תמונות המוצרים יורדות מ-CJ פעם אחת ונשמרות ב-`studio/.cache/p/`.
  - ההמרות של הפריימים נשמרות ב-`studio/.cache/f/`.
  - לכן בנייה חוזרת לא יורדת שוב לרשת.
- **מגבלות:** בסוף הריצה מודפסים מספר הקבצים והגודל. אם `dist` חורג מ-12MB או מ-240 קבצים, הסקריפט יוצא עם קוד 2.
- `studio/dist/` ו-`studio/.cache/` נמצאים ב-`.gitignore`.

| קובץ | מה |
| --- | --- |
| `studio/build.py` | קורא את כל הקלט ובונה את `dist/` |
| `studio/src/index.html` | הדף עצמו: HTML, ‏CSS ו-JS בקובץ אחד, בלי framework ובלי build step. ‏`build.py` מעתיק אותו ל-`dist/index.html` |
| `studio/apply_edits.py` | מסנכרן לריפו את מה שנערך בסטודיו (ראו בהמשך) |
| `dist/data.json` | כל הנתונים שהדף מציג, מחושבים מהריפו |
| `dist/img/p/<id>.webp` | התמונה הראשונה של כל מוצר, 360px בצלע הארוכה, איכות 72 |
| `dist/img/f/<name>.webp` | פריימים ורינדורים, 1280px, איכות 78 |
| `studio/screens/` | צילומי מסך מהבדיקה המקומית |

### בדיקה מקומית

```bash
cd studio/dist && python3 -m http.server 8765
# ופותחים http://localhost:8765/
```

מקומית אין db. לכן ההחלטות, העריכה, ההגדרות והתקציב מוצגים לקריאה בלבד, עם השורה "כדי לערוך, פתח/י את הדף ב-claude.ai".

### פרסום (המנהל)

1. מפרסמים את `studio/dist/index.html` עם כל שאר הקבצים ב-`dist/` (‏`data.json` וכל `img/`), כקבצים נלווים באותם נתיבים יחסיים.
2. מצהירים על capabilities ‏`{db:{}, user:{}}`.
3. זורעים את collection ‏`decisions`: מסמך לכל החלטה, במזהה שלה (T1, ‏D1...), עם השדות של `status/decisions.json`. הדף עצמו לא זורע.

## ה-db של הדף

| מסלול | מי כותב | מבנה |
| --- | --- | --- |
| `decisions/<id>` | המנהל זורע; הדף כותב `update` בלבד | השדות של `status/decisions.json`. תשובה: `{status:"answered", answer:{option, note, at, by}}` |
| `product_edits/<product id>` | הדף, `set` של כל המסמך | `{fields:{רק שדות ששונו}, history:[{at, by, changes:[{field, from, to}]}], synced:false, updated_at}` |
| `product_new/<auto id>` | הדף, `add` / `set` / `delete` | `{url, room, slot, name, cost_usd, note, links, created_at, by, updated_at, synced:false}` |
| `settings/economics` | הדף | הערכים של ההנחות (ראו "רווחיות") ו-`verified:{<key>: bool}` |
| `settings/budget` | הדף | `{rows:[{id, label, one_time_ils, monthly_ils, note, verified}]}` |

### המבנה של `fields` במסמך תיקון

אותו מבנה כמו בכרטיס המוצר, ורק עם השדות ששונים מהריפו:
- `name`, ‏`status`, ‏`rooms` ו-`notes`.
- `slot` + `slot_room`.
- `supplier.product_url` ו-`supplier.sku`.
- `price.cost`.
- `links: [{label, url}]`.
- `economics.{shipping_cost_usd, sell_qty, retail_ils, compare_at_ils}`. ‏`shipping_cost_usd` הוא ליחידה; ‏`sell_qty` הוא מספר שלם ≥ 1.

שדה שחוזר לערך שבריפו יוצא מ-`fields`. ההיסטוריה נשמרת: 50 השינויים האחרונים.

## סנכרון לריפו: `apply_edits.py`

1. המנהל מייצא את ה-db לקובץ JSON. בכפתור "קובץ סנכרון" במסך המוצרים יש בדיוק את המבנה הזה, עם כפתור העתקה:

   ```json
   {"product_edits": [{"id": "...", "data": {...}}], "product_new": [{"id": "...", "data": {...}}],
    "settings": {"economics": {...}, "budget": {...}}}
   ```

2. מריצים:

   ```bash
   python3 studio/apply_edits.py export.json --dry-run   # רק מדפיס diff
   python3 studio/apply_edits.py export.json             # כותב לריפו
   ```

3. בסוף הריצה מודפסת רשימת ה-id-ים שסונכרנו. אפשר גם לשמור אותה לקובץ עם `--out`. אחרי ריצה אמיתית המנהל מסמן `synced:true` על המסמכים האלה, והצ'יפ "ממתין לסנכרון" נעלם. כדאי לבנות מחדש את הסטודיו ולפרסם, כדי שהבסיס יכלול את השינויים.

מה הסקריפט עושה:
- **כרטיסי מוצר:**
  - מחיל את התיקון על `data/products/**/<id>.json`. נוגע רק בשדות שבסכמה: name, ‏slot, ‏rooms, ‏status, ‏supplier.product_url, ‏supplier.sku, ‏price.cost ו-notes.
  - **קישורים נוספים:** לסכמה אין שדה links, ולכן הם נשמרים בבלוק בסוף ההערות, בין `[studio-links]` ל-`[/studio-links]`. ‏`build.py` קורא אותם משם בחזרה.
  - **העברה לחדר אחר:** העברה של עמדה לחדר אחר מזיזה את הקובץ לתיקייה המתאימה. ‏`--no-move` מדלג על ההזזה.
- **כל או כלום לכל מוצר:** תיקון עם שדה לא תקין (URL שלא מתחיל ב-https, מספר שלילי, `sell_qty` שאינו שלם ≥ 1, סטטוס לא חוקי, עמדה שלא קיימת) לא נכתב בכלל, לא מסומן כמסונכרן, ומדווח.
- **כרטיסים שכבר לא עומדים בסכמה** (כרטיסי `pool` עם `slot: null`): רק שגיאת סכמה **חדשה** שהתיקון יוצר חוסמת. שגיאה שכבר הייתה בריפו מדווחת כ"לא חוסמת". תיקון כלכלה בלבד לא נוגע בכרטיס. הסקריפט אף פעם לא כותב `slot: null` לכרטיס שלא היה בו.
- **פריט פגום לא עוצר את הריצה:** כל תיקון וכל ליד רצים ב-try/except. השגיאה מדווחת, וקבצי הכלכלה וההגדרות נכתבים בכל מקרה.
- **כלכלה:** השדות `shipping_cost_usd`, ‏`sell_qty`, ‏`retail_ils` ו-`compare_at_ils` נכתבים ל-`data/economics/products.json`, וההגדרות והתקציב ל-`data/economics/settings.json`. ‏`updated_at` משתנה רק כשערך באמת משתנה, וקובץ שלא השתנה לא נכתב מחדש.
- **לידים:** לכל ליד חדש נוצר `data/products/leads/<id>.json` בסטטוס candidate. השדות החסרים (colors, ‏materials, ‏visual_weight ותמונות) רשומים בהערה. הרצה חוזרת לא יוצרת את הליד פעמיים. ליד נדחה (לא נכתב, לא מסונכרן, מופיע ב-Problems) כשהקישור שלו או קישור נוסף אינו https, כשהחדר או העמדה לא קיימים ב-`data/slots/`, כשהעלות שלילית או לא מספר, או כששדה טקסט אינו טקסט.
- **ולידציה:** כל כרטיס נבדק מול `data/product-card.schema.json` בוולידטור פשוט. הסקריפט לא משנה את הסכמה.
- **אפשרויות:**
  - `--all` מחיל גם מסמכים שכבר סומנו כמסונכרנים.
  - `--force` כותב גם כרטיס שנכשל בוולידציה.
  - `--root` מריץ על עותק אחר של הריפו.

## רווחיות: איך מחושב כל מספר

**ההגדרות:** ברירות המחדל בדף ← `data/economics/settings.json` ← `settings/economics` ב-db. כל ערך שלא סומן "אומת" מוצג כ"הערכה". את השער צריך לעדכן.

| הגדרה | ברירת מחדל |
| --- | --- |
| שער דולר-שקל | 3.7 (לעדכן) |
| שיטת משלוח לחישוב | זול (‏`cheapest` של CJ, בדרך כלל 12–50 יום), או עד 20 יום (‏`cheapest_under_20d`) |
| מע"מ | 18% |
| עמלת סליקה | 2% ועוד ₪1.2 לעסקה |
| שמורת החזרות | 5% מההכנסה נטו |
| CAC | ₪40 להזמנה |
| אריזה | ₪0 |
| יעד מרווח | 35% |
| פריטים בהזמנה ממוצעת | 1.4 (מינימום 1) |
| מקדם משלוח בהזמנה משולבת | 1.0 |

**משלוח לכל מוצר.** הערך הראשון שקיים מהרשימה:
1. תיקון מהסטודיו.
2. `shipping_cost_usd` ב-`data/economics/products.json`.
3. `data/economics/freight-cj.json` לפי שיטת המשלוח.

ליד המספר מופיע המקור: "ידני" או "CJ, ‏<תאריך>". מוצר בלי נתון מקבל דגל כתום "חסר משלוח". בשיטה "עד 20 יום", מוצר שאין לו אפשרות CJ של עד 20 יום מקבל "חסר משלוח מהיר" (אין fallback שקט לקו הזול).

**כמות למכירה (`sell_qty`).** כמה יחידות נמכרות בכל מכירה. העלות והמשלוח בכרטיס ובקובצי CJ הם ליחידה.
- ערך שנקבע בסטודיו או ב-`data/economics/products.json` גובר.
- אחרת ברירת המחדל מחושבת ב-`build.py` (‏`sell_qty_default`): ה-`set_of` של העמדה, כשהשם או ההערות אומרים שהעלות ליחידה; 1 כשהם אומרים שהעלות לסט או לזוג; ו-1 עם צ'יפ "כמות לא ודאית" כשלא ברור.
- משלוח לכמות (הערכה, מסומן "הערכה"): משלוח ליחידה + (כמות − 1) × (משלוח ליחידה − $3.72). לפי בדיקת הסלים של CJ, כ-$3.72 מכל חבילה קבועים והשאר לפי משקל.
- המחיר לצרכן, עלות הנחיתה, התרומה והמחיר המומלץ הם למכירה כולה, וליד כל מחיר מופיע "נמכר כ-N יח'".

**החישוב לכל מוצר** (‏`econCalc` בדף, בין `econ:start` ל-`econ:end`):
- עלות נחיתה ₪ = (עלות × כמות + משלוח לכמות) × שער.
- חלק המשלוח = משלוח לכמות ÷ (עלות × כמות + משלוח לכמות). מעל 50% מסומן.
- הכנסה נטו = מחיר ÷ (1 + מע"מ).
- עמלות = מחיר × סליקה + קבוע.
- שמורה = הכנסה נטו × החזרות.
- תרומה = הכנסה נטו − עלות נחיתה − עמלות − שמורה − אריזה.
- מרווח = תרומה ÷ הכנסה נטו.
- אחרי שיווק = תרומה − CAC ÷ פריטים בהזמנה.
- מחיר מומלץ = (עלות נחיתה + קבוע + אריזה) ÷ ((1 − החזרות − יעד) ÷ (1 + מע"מ) − סליקה). מעוגל למעלה לשקל. אם המכנה לא חיובי, היעד לא אפשרי.

**דגלים:**
- כתום: חסר משלוח, חסר מחיר או חסרה עלות.
- אדום: מרווח מתחת ליעד.
- ירוק: עומד ביעד.

**נקודת איזון:**
- **הבסיס:** הנבחרים עם כל הנתונים. אם אין כאלה, כל המועמדים שלא נדחו ויש להם כל הנתונים.
- **תרומה להזמנה:** פריטים בהזמנה × התרומה הממוצעת − CAC. התרומה הממוצעת מחושבת עם משלוח × מקדם ההזמנה המשולבת.
- **הזמנות לכיסוי ההקמה:** סך החד-פעמי ÷ התרומה להזמנה.
- **הזמנות בחודש:** סך הקבועות ÷ אותה תרומה.

**הזמנה משולבת:** אם קיים `data/economics/freight-bundles.json`, מסך התקציב מציג את החיסכון בכל סל ומקדם ממוצע מוצע. המקדם הוא 1 פחות החיסכון הממוצע, לכל שיטת משלוח. הוא לא מוחל אוטומטית.

**דוגמה שנבדקה** (וילון `curtains-cj-japanese-linen-half-shade`, ברירות המחדל, משלוח זול של CJ ‏$26.67, ומחיר ₪249):

| שלב | חישוב | תוצאה |
| --- | --- | --- |
| עלות נחיתה | (16.58 + 26.67) × 3.7 | ₪160.03 |
| חלק המשלוח | 26.67 ÷ 43.25 | 61.7% |
| הכנסה נטו | 249 ÷ 1.18 | ₪211.02 |
| עמלות | 249 × 2% + 1.2 | ₪6.18 |
| שמורה | 211.02 × 5% | ₪10.55 |
| תרומה | | ₪34.26 |
| מרווח | | 16.2% (אדום) |
| אחרי שיווק | 34.26 − 40 ÷ 1.4 | ₪5.69 |
| מחיר מומלץ | 161.23 ÷ (0.60 ÷ 1.18 − 0.02) | ₪330.06, כלומר ₪331 |

במחיר ₪330.06 המרווח יוצא בדיוק 35%.

## מאיפה כל מספר מגיע (שאר המסכים)

הכול מחושב מהקבצים, ושום מספר לא כתוב ביד. מספרי העמדות והסטטוסים מתעדכנים גם לפי תיקונים מהסטודיו שעוד לא סונכרנו.

| נתון | מקור וחישוב |
| --- | --- |
| חדרים ופריימים | `docs/house-plan.json` ‏`rooms[]`: כל חדר עם `slots_file`. חדרי הילד והילדה חולקים את `data/slots/kids.json`, ולכן הם חדר אחד בסטודיו |
| עמדות | `data/slots/<room>.json` ‏`slots[]`. הפריימים של כל עמדה לקוחים מ-`frames`; אם אין (סלון), הפריימים של החדר. "רק במעבר" מגיע מ-`slots_1_1.<room>.transit_only` |
| שיוך מוצר לעמדה | לפי הנתיב. `data/products/<slot>/` = סלון. `data/products/<room-dir>/<slot>/` = חדר אחר (‏`entrance` = כניסה, ‏`dining` = מטבח ופינת אוכל). `data/products/pool/` = מאגר משותף. `data/products/leads/` = לידים מהסטודיו, והחדר נלקח מ-`rooms` |
| מועמדים משותפים | עמדה שהשדה `shared` שלה מפנה ל-`data/products/<dir>/` או ל-`data/slots/<room>.json <slot>` מקבלת גם את הכרטיסים משם. בטבלה הם מוצגים בנפרד |
| עמדה מכוסה | לפחות 3 כרטיסים שלא נדחו, ישירים ומשותפים |
| כפילויות | אותו `supplier.sku` או אותו pid (מתוך `product_url`) |
| תקנים CE / IP44 / EN71 | זיהוי טקסט בהערות בלבד. ברירת המחדל: "לא ידוע". "לא מאומת": מוזכר רק ליד "not verified", ‏"missing", ‏"no" וכדומה. "מוצהר בהערות": ציטוט של הצהרת ספק ("stated", ‏"PASS", ‏"certifications:"), לא תעודה |
| שלבים ויומן | `status/board.md`: הסעיפים "שלב N", הסימונים `[x]` / `[~]` / `[ ]`, ושורות `- תאריך · סוכן · טקסט` |
| החלטות | `status/decisions.json`, כגיבוי סטטי. החדרים של כל החלטה מוסקים מהטקסט, או נלקחים משדה `rooms` אם יתווסף |
| commit | `git rev-parse --short HEAD`, וגם רשימת הקבצים בקלט שעוד לא נשמרו ב-commit |

## המסכים

1. **סקירה:**
   - כמה החלטות מחכות ומה חוסם.
   - התקדמות לכל שלב 0–4.
   - מוצרים לפי סטטוס, וכמה ממתינים לסנכרון.
   - רווחיות: מרווח ממוצע, דגלים, ומוצרים שבהם המשלוח הוא יותר ממחצית העלות.
   - תקציב ונקודת איזון.
   - כרטיס לכל חדר.
   - 6 שורות היומן האחרונות, ומאיזה commit נבנה הדף.
2. **החלטות:**
   - כרטיס לכל החלטה, עם האפשרות המומלצת, מה ההחלטה חוסמת, וסטטוס.
